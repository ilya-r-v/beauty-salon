# Салон красоты — КР2 (JavaFX)

Настольное приложение на JavaFX для той же предметной области и той же базы
данных PostgreSQL, что в КР1. Подключение к БД — отдельное, напрямую через
JDBC (параметры в `src/main/resources/database.properties`), без веб-сервера.

## Архитектура

```
View (FXML) -> Controller -> Service -> Repository / JDBC -> PostgreSQL
```

- **FXML** (`src/main/resources/fxml/`) — разметка окон и диалогов.
- **Controller** (`fx/controller/`) — реагирует на действия пользователя,
  вызывает сервисы, обновляет таблицы. Никакого SQL здесь нет.
- **Service** (`service/`) — те же классы, что в КР1 (`BookingService`,
  `ClientService`, `ServiceCatalogService`) с теми же бизнес-правилами.
- **Repository** (`repository/`) — те же JDBC-реализации из КР1.
- **model/exception/util** — перенесены из КР1 без изменений, кроме
  `DatabaseManager`, который теперь читает параметры из
  `database.properties`, а не хранит их в коде.

`fx/ServiceRegistry.java` — общая точка доступа к сервисам: каждый
FXML-контроллер создаётся `FXMLLoader`-ом отдельно и не может получить
зависимости через конструктор, поэтому все репозитории и сервисы собраны
здесь один раз.

        ├── BookingDialogController      — форма добавления/редактирования записи
        ├── ClientsTabController         — клиенты и мастера
        ├── ClientDialogController       — форма клиента

## Как запустить

1. Поднимите PostgreSQL с базой `beauty_salon` (как в КР1) и выполните
   `sql/schema.sql`, если база ещё не создана:
   ```
   createdb beauty_salon
   psql -d beauty_salon -f sql/schema.sql
   ```
2. Проверьте/поправьте `src/main/resources/database.properties` —
   url/логин/пароль должны совпадать с вашей установкой.
3. Запустите приложение:
   ```
   mvn clean javafx:run
   ```
   либо откройте проект в IntelliJ IDEA — она подтянет зависимости из
   `pom.xml` сама, и запустите `BeautySalonFxApplication` напрямую.

Docker не требуется: в отличие от примера из архива задания (где
JavaFX обращается к Spring Boot backend через REST), это приложение
подключается к PostgreSQL прямо по JDBC — так, как и просит задание КР2
для собственного варианта.

## Что реализовано

**Главное окно** — 4 вкладки: «Записи на услугу» (основная сущность),
«Клиенты и мастера», «Услуги», «Статистика».

**Записи на услугу** — полный CRUD через диалог с ComboBox для выбора
клиента/мастера/варианта услуги (пользователь не вводит UUID вручную);
подтверждение перед удалением; поиск по имени клиента и по названию
услуги; фильтрация по статусу, по мастеру и по диапазону дат (три
фильтра, можно сочетать); сортировка по дате и по статусу; экспорт в
`.xlsx` через `FileChooser` (пользователь сам выбирает путь).

**Клиенты и мастера** — CRUD клиента, поиск по имени и по телефону,
назначение клиента мастером.

**Услуги** — создание типов услуг, услуг (с выбором мастера и типа через
ComboBox) и вариантов с ценой; фильтрация по мастеру и по типу; удаление
с проверкой бизнес-правил.

**Статистика** — 7 показателей: клиенты, мастера, записи по каждому из
4 статусов, выручка по завершённым записям, средний чек.

## Бизнес-правила (без изменений по сравнению с КР1)

**BookingService:** несуществующий клиент/мастер, запись в прошлое,
занятость мастера на то же время, запрещённые переходы статуса
(`PENDING → CONFIRMED → COMPLETED`, либо `→ CANCELLED`), запись без
варианта услуги, изменение/удаление завершённой записи.

**ClientService:** обязательные имя/телефон, несуществующая роль,
повторное назначение мастером, удаление клиента с активными записями.

**ServiceCatalogService:** несуществующий мастер/тип при создании услуги,
цена варианта ≤ 0, несуществующая услуга у варианта, удаление услуги
с оставшимися вариантами.

Все проверки выполняются в слое `service`, а не в контроллерах — там
контроллер только показывает `errorLabel`/`Alert` с текстом сообщения,
которое бросил сервис.

## Обработка ошибок

- Текст вместо числа (цена) — проверяется до вызова сервиса, диалог не
  закрывается, выводится понятное сообщение.
- Нарушение бизнес-правила — `BusinessException` ловится в контроллере,
  текст показывается в `errorLabel` диалога или в `Alert`, окно остаётся
  открытым для исправления.
- Отсутствие записи по ID (например, если её удалили из другого места) —
  `EntityNotFoundException` обрабатывается так же, без падения программы.
- Ошибка подключения к БД/SQL — `RuntimeException` из репозитория дойдёт
  до `Alert` с сообщением; приложение не закрывается.
